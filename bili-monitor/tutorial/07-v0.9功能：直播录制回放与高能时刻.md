# v0.9 功能：直播录制回放与高能时刻

> **⚠ v2.2 架构改版（2026-10-12）**：capture 采集进程与录制/转码/上云管线已
> 整体迁 replay 项目（本文对应章节为历史口径，操作以 replay/deploy/README.md
> 为准）；本项目仅剩 web 服务，共享数据库经 [server].db_path 指向
> /opt/replay/data/live.db。高能时刻功能已移除。

> 本章对应 v0.9 版本新增的两块功能：**整场录制回放**（监控码 + 极简按钮页）
> 与**高能时刻**（弹幕/礼物高能片段自动剪辑）。两者共享同一条 ffmpeg 录制
> 链路，在代码里是一起实现的（`bili_monitor/capture/recording.py` 是公共基建）。
> v0.10 在此链路上追加**视频外挂弹幕**（见 1.4）并修复出片双缺陷（见 2.2
> 与 5 节的 v0.10 修正说明）。

## 1. 功能一览

### 1.1 整场录制回放（replay 按钮页）

给主播本人或指定用户一个"自助录播"入口，全程不接触监控系统的任何其他页面：

```
访问 http://<服务器IP>/bili-monitor/<房间号>/replay
  → 未登录：跳转专属登录页 /<房间号>/replay/login（昵称 + 监控码两个输入框）
  → 输入昵称与监控码登录 → 进入极简按钮页（一个大按钮 + 录播列表）
  → 点按钮开始整场录制（v0.9.1 起 qn=200，4K 超清档）
  → 再点一次 / 主播下播 → 自动停止并保存成 mp4
  → 列表出现新条目，可预览（浏览器内播放）、下载、添加注释（v0.9.2，见 1.2）
  → 管理员可给条目命名、所有人可按名字/注释搜索（v0.10.1，见 1.5）
  → 成片保留 30 天（另有磁盘水位兜底，见第 5 节）
```

三个关键设计（需求确认时的决策）：

- **监控码一房一码**：码格式 `r<房间号>-<10位随机>`，明文存在 `rooms.replay_code`
  列，在「直播间管理」页生成/重置/复制（仅管理员可见）。持码登录后的会话
  被中间件锁定为"只能操作这个房间的按钮页、录制接口与录像文件"——访问
  任何其他页面都会被弹回自己的按钮页，任何监控数据 API 都返回 403。
- **仅限监控名单内的房间**：房间必须先加进监控（`rooms` 表且 enabled=1），
  管理页才会为它生成监控码。
- **未开播不能开始**：点击时房间未开播，录制请求会被标记失败并在按钮页
  toast 提示"当前未开播"。

### 1.2 录制注释（v0.9.2）

按钮页已保存的录播条目可以**添加注释**：每个登录的人各注各的，互相可见，
但只能修改/删除**自己署名**的注释（管理员也不例外）。注释区默认折叠，
点条目右侧「注释 (N)」按钮展开，N 为已有条数。

身份怎么来（监控码是"一房一码"、多人共用，本身区分不了人）：

- **登录时填昵称**：v0.9.2 起专属登录页有两个输入框——昵称 + 监控码。
  昵称随监控码一起校验通过后**写进签名 Cookie**（百分号编码，支持中文，
  最长 16 字符），此后 30 天会话期内不可更改；
- **署名 = 身份**：注释表存 `author` 字符串（replay 会话=登录昵称、admin=
  管理员用户名），API 只按"署名与当前会话一致"判定能否改删。同码使用者
  之间是信任关系：有人用相同昵称登录即可冒充——这是共享监控码模型下的
  已知取舍，不做强认证；
- **旧会话兼容**：v0.9.2 之前签发的 replay 会话没有昵称，录制功能照常
  用，但点开注释区会提示"重新登录后可添加注释"（admin 身份不受影响）；
- 注释随录制行**级联删除**（30 天清理/水位删除时一起消失），长度上限
  500 字，多人注释按时间正序展示；页面 2.5s 轮询重建列表时**输入草稿与
  编辑态自动回填**，不会打到一半被清空。
- **删除录播（v0.10，仅管理员）**：终态条目右侧有「删除」按钮（红色悬停），
  二次确认后成片文件、遗留分段目录、DB 行与全部注释一并删除。该按钮只在
  **管理员登录的入口**渲染——监控码会话看不到按钮，API 侧同样仅 admin 放行
  （replay/guest 一律 403），进行中的录制不可删（409，先停止再删）。

### 1.3 高能时刻

对已监控的直播间做"预录屏 + 高能剪辑"：

- 总览页每行新增「高能」开关（默认关，仅管理员可点）；开启后 capture 服务
  在该房间开播时自动起一路**滚动缓冲**录制（只保留最近约 5.5 分钟的分段）；
- 每场直播按 **3 分钟窗口**统计弹幕量与礼物营收（两轨独立）；窗口值超过
  本场历史最高、且达到最低阈值（弹幕 ≥30 条 / 礼物 ≥10 元）时，保存
  **该窗口结束时刻的前 5 分钟 + 后 3 分钟**片段（共 8 分钟）；
- 出现新的最高时，**删除上一条成片**（数据库行保留并标记 superseded）；
- **天选弹幕不计入高能统计**（主播开天选时刻观众按口令刷屏，会被误判成
  "高能"）：协议层接住 `ANCHOR_LOT_CHECKSTATUS` 消息取口令排除，另有
  启发式兜底（60 秒内同一文本弹幕 ≥15 条视为刷屏口令）；
- 开播**前 5 分钟**的窗口只统计不评估（主播刚开播调整设备的杂音期不算）；
- 场次详情页（`/session/<房>/<场次>`）「高能时刻」板块：弹幕高能、礼物高能
  两组，行内 `<video>` 直接播放（v0.10 起仅场次详情页渲染——直播间详情页
  不显示该板块，直播中跟随最新场次轮询的旧展示逻辑已移除）。

### 1.4 视频外挂弹幕（v0.10）

v0.9 的两处视频播放点（按钮页整场预览、详情页高能板块）都叠加了**弹幕
显示**——外挂（播放时渲染）而非烧录（录制时画进画面）：

- **为什么外挂**：烧录必须整条重编码，qn=200 的 4K 成片在 2 核服务器上是
  小时级计算，且会破坏 `-c copy` 秒级拼接与磁盘水位管理；外挂方案服务器
  只查 SQLite 弹幕表下发 JSON（gzip 后 MB 级），渲染全在浏览器 canvas 上，
  资源压力近乎为零；
- **对齐原理**：ffmpeg 分段文件名 `seg_日期T时间.ts` 自带墙钟时间。成片
  收尾（整场 concat 前 / 高能挑段后）把段名序列转成「墙钟 → 视频内偏移」
  映射（`recording.build_timeline`）存进 `recordings.timeline` /
  `he_clips.timeline` 列——每个 ffmpeg 连续运行段（run）一行，断流重连
  产生的时间轴跳变由此吸收到 ±1 分段（10 秒）内；
- **弹幕接口只给 `{t, text, guard}` 三个字段**——不返回 uname/uid：监控码
  角色可访问整场弹幕接口（挂在 replay 白名单前缀下），必须保持其对用户
  身份信息零接触的边界。`guard`（1总督/2提督/3舰长）仅供前端着色
  （橙金/粉/蓝）；
- **渲染层 `web/static/danmaku.js`**（自写 ~300 行，零依赖不引播放器库）：
  canvas 绝对定位盖在原生 `<video>` 上（pointer-events:none，不挡控件），
  以 `video.currentTime` 为时钟——拖进度/暂停/倍速天然正确；轨道分配 +
  密度限流（天选口令刷屏自然被截断）；控制条有弹幕开关、**±10s 微调**、
  密度档、不透明度（前三者 localStorage 持久化）；
- **对齐误差口径（重要）**：直播弹幕相对画面有 3~10 秒固有延迟（观众自己
  看直播也有延迟 + 流延迟），B 站官方录播同样存在——用控制条「微调」
  ±10s 吸收，属正常现象而非 bug；
- **存量成片降级**：v0.10 之前收尾的成片没有 timeline（分段已被删，信息
  不可恢复），接口以开始时间为原点做单 run 近似并标 `approx:true`，前端
  显示「时间轴近似」标记——断流重连过的旧录像弹幕可能错位且无法修复；
  新录制不受影响；
- 纯表情弹幕（如只发一个 [dog]）不渲染；混合弹幕的 `[表情]` 占位符按原
  文本显示（不请求图片，保持零外部依赖）。

### 1.5 录播命名与列表搜索（v0.10.1）

录播多了两个小功能，都长在按钮页的已保存列表上：

- **命名（仅管理员可改）**：管理员入口的终态条目右侧有「命名 / 重命名」
  按钮（有名字后按钮文案变「重命名」），点开是行内编辑框——保存即 PATCH
  到 `recordings.title` 列（去首尾空格、最长 60 字，**留空保存 = 清除名字**）。
  名字以粗体展示在条目时间的旁边，监控码使用者**只能看不能改**：按钮只在
  管理员会话渲染，API 侧与删除录播同口径在路由内收紧为仅 admin（replay/
  guest 一律 403）。进行中的录制行也可以先命名（纯元数据，不碰状态机）；
  页面 2.5s 轮询重建列表时编辑草稿自动回填并恢复焦点；
- **搜索框（所有人可用）**：已保存列表上方有搜索框，输入即**纯前端过滤**
  ——名字、任一注释的内容或署名，任一包含搜索词（不区分大小写）即保留
  该条目；无命中显示「没有名字或注释包含『××』的录播」。列表数据本来就
  随轮询整表下发（每房间 30 天内的行数很小），前端过滤不需要服务器参与。

## 2. 两功能如何共享一条录制链路（架构核心）

服务器只有 2 核 / 1.7G 内存 / 约 10Mbps 入带宽，录制方案的一切设计都围绕
"**不转码、少开进程、少占带宽**"：

```
                     ┌─ 整场录制（手动，qn=200）──→ 全部分段保留 ─→ concat 成整场 mp4
一路 ffmpeg（每房间）┤
（-c copy 纯转封装） └─ 高能缓冲（开关，qn=80）─→ 滚动清理保留出片窗口+裕量
                                  └→ 高能触发时从分段里原地挑 [T-5min, T+3min] 出片段
```

- **清晰度就高**：每房间同时最多一路流。整场录制（200）进行中时，高能
  片段直接引用整场分段（画质更高且不缺片段）；没有整场录制时高能自己起
  80 流。整场开始时若 80 流在跑，会切换重启为 200 流（切换丢失 <10 秒）。
- **web 进程不碰 ffmpeg**：按钮页的"开始/停止"由 web 写一条 `recordings`
  表的行（状态 requested / stop_requested），capture 服务里的**2 秒扫描
  循环**捡起后真正启停 ffmpeg（`manager._scan_recordings`）。这样录制进程
  全部收在 capture 的 systemd 服务里（MemoryMax 600M 统一管控），web 保持
  轻量（200M 不变）。
- **开播校验在 capture 侧**：请求行被捡起时现查一次房间状态，未开播的
  行改成 failed + 原因"当前未开播"，按钮页轮询列表就能看到并提示。
- **断流自动续录**：B 站直链带鉴权 token 且时效短（分钟级），因此每次
  起流/断流重启都重新调接口取新地址（三层兜底见下）；ffmpeg 意外退出且
  房间仍在播时，watcher 协程按指数退避（5s→60s 封顶）自动续段，**同一场
  录制不拆文件**。
- **下播自动停止**：跟随场次状态机的宽限逻辑（`end_grace_sec` 默认 10
  分钟）——短暂"假下播"期间流断了也不收尾，复播后自动续上；确认下播才
  concat 保存。用户手动点停止则立即收尾。

### 2.1 拉流地址三层兜底（`recording.fetch_playurl`）

B 站没有公开的拉流文档，三个接口依次尝试、宽松解析，全部走项目现成的
登录 cookie 会话（`build_bili_session`，防风控）：

1. `xlive/web-room/v2/index/getRoomPlayInfo`（web 端现行接口，返回
   `playurl_info` 结构，优先取 flv 流，其次 hls_fmp4）；
2. `room/v1/Room/playUrl`（老接口，返回 durl 直链列表）；
3. `getInfoByRoom` 响应里自带的 `playurl_info`（结构与 ① 相同）。

**踩坑实录（2026-10-01 实测）**：直链 CDN 会校验请求头——ffmpeg 默认
User-Agent（Lavf/...）直接 403。解决：ffmpeg 命令加 `-headers`，带与浏览器
同款的 User-Agent 和 `Referer: https://live.bilibili.com/`（见
`recording.FFMPEG_HEADERS`）。

另一个实测结论：**qn 是请求上限而非指定值**——请求 qn=200 时，若主播推流
本身是 250（原画）档，接口按实际推流返回。这不影响功能（拿到的就是主播
最高画质），只是磁盘占用按实际码率估算。

### 2.2 目录布局（`data/recordings/<房间号>/`）与出片两处 v0.10 修正

```
full_<录制id>/seg_*.ts   整场分段（mpegts，10 秒/段，文件名即时间戳）
full_<录制id>.mp4        整场成片（concat + remux 产物，+faststart）
buffer/seg_*.ts          高能滚动缓冲（清理协程保留「出片窗口+裕量」≈620s）
clips/he_<片段id>.mp4    高能成片
ffmpeg.log               ffmpeg stderr（排障：403、直链过期等只报在这里）
```

（v0.9 的 `pending/<片段键>/` 出片工作区已随 v0.10 移除，遗留目录由每日
维护任务清扫。）

分段用 mpegts 容器是因为它**中断安全**（每段自同步，进程被杀也不损坏已写
的段）；停止后用 `ffmpeg -f concat -safe 0 -c copy -movflags +faststart` 拼
成 mp4——纯转封装无转码，1 小时录像几秒到几十秒完成，CPU 占用个位数。
`+faststart` 把 moov box 移到文件头，浏览器 `<video>` 才能边下边播、拖动
进度条（配合 web 端 StaticFiles 原生的 HTTP Range 支持）。

**v0.10 出片双缺陷修正**（历史实证记录未随本公共仓发布）：

1. **双轨出片分段竞争**（v0.9.2 已知bug）：v0.9 的 `record_clip` 出片前把
   buffer 分段**移入** pending 工作区防清理，同窗口 danmaku/gift 两轨并发
   出片时后者扫不到被移走的分段必然失败。v0.10 改**原地只读** concat——
   两个 ffmpeg 并发只读同一批已封闭 TS 文件安全，竞争消失；
2. **缓冲保留期截短成片**（v0.10 评估时新发现，与 ① 同源）：v0.9 清理协程
   只保留 `buffer_sec×1.1`（≈330s）分段，而出片发生在触发后 ~200s 且需回看
   300s——最老分段届时已 ~510s，**v0.9 起所有缓冲流模式的高能成片实际只有
   ~5min10s（设计 8min）**，「移入 pending」从未覆盖真正需要的窗口。v0.10
   保留期改为 `buffer_sec + post_sec + 2×segment_sec + 120s 裕量`（默认
   620s，`_buffer_keep_sec()`）。

## 3. 数据库与 API

### 3.1 新增表（db.py SCHEMA，幂等迁移）

- `recordings`：整场录制。状态机
  `requested → recording → stop_requested → finalizing → finished / failed / interrupted`
  （interrupted = capture 重启或房间被移除时对"已录部分"的收尾保存）；
- `recording_notes`：录制注释（v0.9.2）。`author` 存署名字符串（replay 会话=
  登录昵称、admin=用户名），随 recordings 行级联删除；
- `he_windows`：每 3 分钟窗口一行统计（为后期数据分析图表预留）；
- `he_clips`：高能成片（status: saving/finalized/failed/superseded）；
- `rooms` 加两列：`record_enabled`（高能开关）、`replay_code`（监控码明文）；
- v0.10：`recordings` / `he_clips` 各加 `timeline` 列——「墙钟 → 视频内偏移」
  映射 JSON（`{"runs":[{wall,off,dur}],"approx":false}`），外挂弹幕对齐用；
  空串 = v0.10 前的存量行（接口走单 run 近似并标 approx）；
- v0.10.1：`recordings` 加 `title` 列——管理员命名的名字（空 = 未命名，
  ≤60 字），列表接口随行带出，前端展示并参与搜索过滤。

### 3.2 新增 / 变更 API

| 接口 | 说明 | 权限 |
|---|---|---|
| `POST /api/replay/login` | 监控码登录（v0.9.2 起需带昵称），签发绑定房间的 replay 会话 | 免登录 |
| `GET /{room_id}/replay` / `/{room_id}/replay/login` | 按钮页 / 专属登录页 | admin 或该房 replay |
| `GET /api/rooms/{id}/recordings` | 录制列表（进行中带实时体积；v0.9.2 起每行带 notes） | admin / 该房 replay |
| `POST /api/rooms/{id}/recordings/start` | 请求开始（写 requested 行） | admin / 该房 replay |
| `POST /api/rooms/{id}/recordings/{rid}/stop` | 请求停止并保存 | admin / 该房 replay |
| `DELETE /api/rooms/{id}/recordings/{rid}` | 删除终态录播（v0.10：成片+分段目录+行+注释级联；按钮页删除入口） | 仅 admin |
| `PATCH /api/rooms/{id}/recordings/{rid}` | 录播命名/改名（v0.10.1：body `{title}`，空串清除，≤60 字；按钮页命名入口） | 仅 admin |

| `PATCH /api/rooms/{id}/recordings/{rid}/notes/{nid}` | 修改注释（仅作者本人） | admin / 该房 replay |
| `DELETE /api/rooms/{id}/recordings/{rid}/notes/{nid}` | 删除注释（仅作者本人） | admin / 该房 replay |
| `POST /api/rooms/{id}/record` | 高能开关（写 rooms.record_enabled） | 仅 admin |
| `GET /api/rooms/{id}/high-energy` | 高能片段列表（详情页板块） | admin / guest |
| `GET /api/rooms/{id}/recordings/{rid}/danmaku` | 整场成片的外挂弹幕（v0.10，只含 t/text/guard） | admin / 该房 replay |
| `GET /api/rooms/{id}/clips/{cid}/danmaku` | 高能成片的外挂弹幕（v0.10，只含 t/text/guard） | admin / guest |
| `POST /api/rooms/{id}/replay-code/reset` | 生成/重置监控码 | 仅 admin |
| `GET /api/rooms` | 新带 record_enabled；replay_code 仅 admin 响应携带 | 登录即可 |

注释三接口挂在 `/api/rooms/<房>/recordings` 前缀下——正是中间件为 replay
角色放行的唯一 API 前缀，因此天然继承"只能操作本房间"的隔离；改删权限
在路由内按"author == 当前会话署名"校验（管理员不能改别人的注释）。

录像文件走 `app.mount("/recordings", StaticFiles(...))`，处于登录保护内；
replay 角色仅能访问 `/recordings/<自己房间>/` 前缀。

## 4. 监控码分发流程（日常使用）

1. 管理员登录 → 「直播间管理」页 → 目标房间行「生成监控码」（或对已有码
   点「重置」换新，旧码立即失效）；
2. 把两样东西发给使用者：**监控码** + 按钮页地址
   `http://<服务器IP>/bili-monitor/<房间号>/replay`；
3. 使用者打开地址 → 输入自选昵称与监控码登录 → 点按钮录制。全程看不到
   任何监控数据；
4. 明文码同时追加备份在服务器 `/opt/bili-monitor/data/web_credentials.txt`
   （`data/web_credentials.txt` 同机制）。

## 5. 磁盘权衡（重要，使用前必读）

服务器盘共 40G（系统+项目已用约 4G）。v0.9（qn=150）档实测约 **450MB/小时**；
  v0.9.1 起 qn=200（4K 档），真 4K 推流主播可达 **3.5~6.7GB/小时**
（按主播实际码率浮动，1~1.3GB/小时的极端情况也存在），因此：

- **保留期**：整场 30 天（`full_retention_days`）、高能 14 天
  （`clip_retention_days`），每日 04:00 维护任务清理（文件+行一起删）；
- **水位兜底**：整场总量超 `max_total_full_gb`（默认 8GB）、高能超
  `max_total_clips_gb`（默认 2GB）时**从最旧开始删**，防盘爆；
- **v0.10 缓冲留存加大**：高能缓冲分段保留期从 ~330s 提到 ~620s（修复成片
  被截短，见 2.2），qn=80（约 1~2Mbps）下每房间缓冲约 80~160MB，
  5 路并发 <1GB——40G 盘可承受，但巡检磁盘时别忘了这块常驻占用
  （`du -sh /opt/bili-monitor/data/recordings/*/buffer`）。

**v0.10 配置约束（重要）**：`[retention] danmaku_days`（默认 90）**不得低于**
`[recording] full_retention_days`（默认 30）——弹幕保留期短于成片保留期时，
后段老成片的弹幕已被清理，外挂弹幕会缺失（视频本身不受影响）。调整任一
保留期时两处一起看。

换算：8GB ≈ 6~18 小时成片存量。如果每天录 2 小时，想存满 30 天需要
~27GB（盘装不下）——超水位会**提前删最旧**，这是设计内的取舍。想多存有
两个旋钮：调大 `max_total_full_gb`（盘允许的话），或调小 `full_qn`（画质
换容量）。

## 6. 部署与运维

### 6.1 部署步骤（相对 v0.8 的增量）

1. 服务器安装 ffmpeg：`apt-get install -y ffmpeg`（Ubuntu 26.04 源内版本即可；
   验证 `ffmpeg -version`）；
2. 照旧同步代码（**排除 `data/` 与 `config.toml`**——录播产物在 data/ 下
   不会被误同步）；
3. 修改 `deploy/bili-monitor-capture.service`：`MemoryMax=400M` → `600M`
   （ffmpeg 子进程并入 capture 的 cgroup，每路约 40~60MB；web 保持 200M
   不变，因为它不再起 ffmpeg）→ `systemctl daemon-reload`；
4. 重启 `bili-monitor-capture` 与 `bili-monitor-web` 两个服务（Nginx 无需
   改动）；
5. 验收：四项常规检查 + **录制实测**（监控码登录→点录制→`ps aux | grep
   ffmpeg` 确认进程、`data/recordings/<房间>/full_*/` 分段在增长→停止→
   按钮页出现成片可预览/下载）+ **高能实测**（总览页开开关→等开播→详情
   页看片段）+ 资源复核（`free -h`、`ps -o rss= -C ffmpeg`）。

### 6.1.1 v0.10 部署增量（相对 v0.9.3）

代码含 DB 迁移（`recordings`/`he_clips` 各加 `timeline` 列，`init_db`
幂等 ALTER），部署步骤：

1. **迁移前备份**：`python3 -c "import sqlite3; s=sqlite3.connect(
   '/opt/bili-monitor/data/live.db'); d=sqlite3.connect('/opt/bili-monitor/
   data/live.db.pre-v0.10-<ts>'); s.backup(d)"`（在线备份不中断采集）；
2. 照旧 tar 全量同步（排除 `data/` 与 `config.toml`，关键文件 md5 校验）；
3. 重启 `bili-monitor-capture` 与 `bili-monitor-web` 两服务（Nginx 无改动）；
4. 验收：四项常规 + timeline 列确认（`PRAGMA table_info(recordings)`）+
   重启后快照恢复写入；弹幕对齐与双轨出片属功能实测，待下次开播验证。
   若重启窗口有直播进行，先按工作区 AGENTS.md 数据保全规程托底回灌。

### 6.2 日常运维速查

| 现象 | 排查 |
|---|---|
| 点了录制但一直"启动中" | 看 capture 日志 `journalctl -u bili-monitor-capture -n 50`；requested 行长期不被捡起说明扫描循环异常 |
| 启动后马上失败 | 按钮页条目上有失败原因（未开播/拉流失败）；`data/recordings/<房间>/ffmpeg.log` 看具体报错（403=请求头问题、Connection reset=直链过期重试） |
| 成片为 0 字节 / failed | 同上看 ffmpeg.log；分段目录若还在可手工 `ffmpeg -f concat` 抢救 |
| 磁盘涨得快 | `du -sh /opt/bili-monitor/data/recordings/*`；必要时临时手动清最旧的 full_*.mp4（同时删 recordings 表对应行） |
| capture 重启后录制没了 | 设计行为：重启会对孤儿录制行收尾保存（状态 interrupted），按钮页重新点击即可继续 |
| 高能一直不出片 | 先查 `he_windows` 表是否在写（开播满 3 分钟应每窗一行；0 行=统计链路没跑，看 capture 日志有无 `人气采样异常`——v0.9 曾因 `_settle_window` 误引 `client.queue` 致整链失效）；有统计再看弹幕/礼物量是否达阈值（30 条 / 10 元）、是否开播不足 5 分钟（豁免期）、高能开关是否开启（无录制流不评估） |
| 高能成片时长只有 ~5 分钟 | v0.9 的缓冲保留期截短 bug（设计 8min 实际 ~5min10s），v0.10 已修复；v0.10 前生成的存量片段无法补救，被更高能窗口取代后新片即正常 |
| 播放器里弹幕没显示 / 条数很少 | ① 弹幕开关是否被关（控制条最左按钮，localStorage 记忆）；② 弹幕密度档是否"少"；③ 控制台 Network 看对应 `danmaku` 接口是否 200（404=该行无成片、403=跨房间权限）；④ 老成片弹幕若在 `danmaku_days` 保留期外已被清理（见第 5 节配置约束） |
| 弹幕和画面错位 | 先用控制条「±10s 微调」吸收（观众/流延迟 3~10s 属固有现象）；错位超过 ~15s 且成片带「时间轴近似」标记 → v0.10 前的存量成片且断流过，无法修复；新录制错位超 15s 再排查（正常由 timeline 映射吸收到 ±10s 内） |
| 服务器上 curl 直连 8001 测 `/recordings/...` 返回 404 | 已知行为：应用配置了 `root_path=/bili-monitor`，回环直连（不带前缀）时 StaticFiles 路径计算会差一层前缀；**经 Nginx 的公网访问（带 `/bili-monitor/` 前缀）正常**，验收与运维请用公网地址测 |

### 6.3 关键配置（config.toml `[recording]` 段）

全部参数见 `config.example.toml` 内注释。最常动的三个：
`full_qn`（按钮页画质）、`max_total_full_gb`（整场磁盘水位）、
`enabled`（功能总开关，本地没装 ffmpeg 时可 false 完全关闭）。
