# 06-v0.5功能：登录双角色与运营功能

> 本章对应 v0.5（2026-09-16 交付）：登录体系升级、主播描述与标签、场次标题、用户分层新口径、数据分析页、以及若干界面调整。讲解按"功能是什么 → 代码在哪 → 怎么运维"组织，供入门读者理解这一批功能的完整实现链路。

## 1. 登录体系：管理员 / 游客双角色

### 1.1 功能与页面

- 访问任何页面未登录时：页面 302 跳转 `/login`，API 返回 401；
- `/login` 登录页（`web/templates/login.html`）两种模式：
  - **管理员**：账号 + 密码，全站读写（房间增删、描述/标签编辑等）；
  - **游客**：游客码，全站只读（写 API 一律 403，导航隐藏管理入口）；
- 登录成功签发 **30 天 HttpOnly 签名 Cookie**，右上角显示当前身份与登出入口。

### 1.2 实现链路（代码地图）

| 环节 | 文件 | 要点 |
|---|---|---|
| 口令哈希 / 签名 Cookie | `web/auth.py`（v0.5 新增） | stdlib PBKDF2-HMAC-SHA256（12 万迭代+随机盐）；Cookie 值 = `过期时间戳\|角色\|用户名\|HMAC签名`，密钥 `data/web_secret.key` 首次启动自动生成 |
| 账户存储 | `db.py` 中 `admin_users` / `app_secrets` 表 | 只存哈希；首次启动 `seed_web_credentials()` 播种默认 admin（16 位随机）与游客码（12 位），明文一次性写 `data/web_credentials.txt` |
| 登录/登出/身份接口 | `web/app.py` 的 `/api/auth/login`、`/api/auth/logout`、`/api/auth/me` | 登录失败 401 不区分账号/密码错误（防枚举） |
| 全站拦截 | `web/app.py` 的 `auth_gate_and_no_cache` middleware | 白名单：`/login`、`/static`、`/api/auth/login`；未登录页面 302 / API 401；游客调写方法（POST/PUT/DELETE/PATCH）403 |
| 旧通道兼容 | `check_admin()` | `X-Admin-Token`（或 body `token`）等于 config 的 `admin_password` 时视为管理员——历史脚本无改动继续可用 |
| 强制登录开关 | `config.toml` 的 `capture.admin_password` | **为空 = 本地调试模式不强制登录**；非空（生产）启用上述全部拦截 |

### 1.3 运维

- **凭据**：明文在 `/opt/bili-monitor/data/web_credentials.txt`（首次启动自动生成）；
- 重置游客码：管理员登录后 `POST /api/admins/reset-guest-code`（新码仅响应返回一次）；
- 添加/删除管理员：`POST / DELETE /api/admins`（不开放注册；至少保留一个、不能删当前登录账户）；
- 忘记管理员口令：登录服务器操作 `data/live.db` 的 `admin_users` 表（删行后重启 web 服务会重新播种并写凭据文件）；
- Nginx 的 Basic Auth 已于 v0.5 移除（htpasswd 文件保留在 `/etc/nginx/.htpasswd_bili` 备回退，加回两行 `auth_basic` 即可恢复）。

## 2. 主播描述与标签（总览页）

- **数据**：`rooms.description` 列（≤100 字）+ `room_tags` 表（每房 ≤8 个、单个 ≤12 字，主键 `(room_id, tag)`）；
- **编辑入口在「直播间管理」页**（`manage.html` 房间表的"描述/标签"两列，行内编辑），总览页两处为**纯展示**（描述为空时兜底显示房间号）；
- API：`PATCH /api/rooms/{id}/description`、`POST/DELETE /api/rooms/{id}/tags[/{tag}]`（管理员）；`GET /api/rooms`、`GET /api/summary` 带出 `description` 与 `tags`（`app.py` 的 `_room_tags()` 一次查询分组）。

## 3. 场次直播标题

- **采集零成本**：120s 状态轮询里的 `getInfoByRoom` 本就返回 `title`，`fetch_room_metrics`（manager.py）透传一个字段即获得数据源；
- **记录**：`poll_live_status` 每轮对比，标题变化即向 `session_titles` 表追加一行（`(session_id, title)` 主键，`last_seen` 持续刷新）；下播清空内存标记，复播同标题也记为新场次首标题；
- **展示**：历史场次"场次"列显示本场的全部标题（多标题每行一个，首行主色），功能上线前的旧场次兜底"第 N 场"；场次详情页副标题带首个标题；
- **合并**：短间隔场次合并（`maintenance.merge_short_gap_sessions`）同步迁移标题，两场同标题时 `UPDATE OR IGNORE` 去重；
- 局限：B 站无历史标题接口，旧场次不回补。

## 4. 用户分层口径（v0.5 定稿）

配置在 `config.toml` 的 `[tier]` 段：

| 层 | 条件 |
|---|---|
| 核心 | 舰长/提督/总督（`user_stats.guard_level` 历史最高 >0，或窗口内有大航海购买记录），**或场均送礼 ≥ `core_gift_per_session_yuan`（10 元）**：窗口内送礼总额 ÷ 参与场次数、分母保底 1 |
| 活跃 | 任一单场弹幕数 ≥ `active_min_danmaku`（10 条） |
| 普通 | 其余 |

- **权威口径**：`maintenance._recompute_user_stats` 每日 04:00 与服务启动时全量重算（规则变更后重启服务即完成存量迁移）；
- **实时跟进**：`writer.py` 的 `_SQL_USER_UPSERT`——舰队消息立即升核心；送礼按"当条消息所属场次累计 ≥10 元"升核心（鸽笼原理保证是场均条件的必要超集，次日凌晨重算收敛）；弹幕按"当条场次计数 ≥10 条"升活跃；
- **历史场次回顾页**：用户榜只显示本场参与用户，核心按"本场送礼 ≥10 元或舰队"计算。

## 5. 数据分析页

- 导航"数据分析" → `/analysis`（`analysis.html`）：主播下拉（覆盖全部在册房间）+ 近 30/90 天切换；
- 概览指标卡：场次数、总时长、总弹幕、总营收、场均弹幕、场均营收、最高同接、活跃观众——`GET /api/rooms/{id}/analysis/overview` 从现有表聚合；
- 4 个图表板块为占位（"后续版本接入"），本期不做空端点。

## 7. 部署与验收记录（2026-09-16）

代码同步（排除 `data/`、`config.toml`）→ `uv sync` → 重启两服务（启动自动建新表/列、播种凭据、新口径重算分层）→ Nginx 删 `auth_basic` 两行并 reload → 五项验收：两服务存活、8001 回环、`nginx -t`、外网未登录 302 `/bili-monitor/login`、管理员/游客登录矩阵（游客写 403）全部通过。日常部署方法见 [05-部署到服务器.md](05-部署到服务器.md)。
