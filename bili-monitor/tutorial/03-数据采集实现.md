# 03 数据采集实现

> **⚠ v2.2 架构改版（2026-10-12）**：本章所述 capture 侧功能（自动全程/切片/
> 直播截取/录制执行）已整体迁 replay 项目，历史口径留档备查。

讲清楚"数据是怎么从 B站拿到的"。核心文件：`bili_monitor/capture/` 六个模块（main / manager / handler / writer / caches / maintenance）。

## 1. blivedm 是什么、怎么用

blivedm 维护了 B站直播弹幕的**私有 WebSocket 协议**：握手鉴权、心跳、消息的 zlib/protobuf 解压解析。我们只用它的公开接口：

```python
# manager.py 的 _ws_loop（简化）
client = blivedm.BLiveClient(room_id, session=http_session)  # 复用带 cookie 的会话
client.set_handler(EventRouter(...))                          # 注册回调路由
client.start()
await client.join()    # 阻塞到断线，退避后重连（指数退避，上限 60s）
```

要点：`session` 传的是我们自己构造的 aiohttp 会话（浏览器 UA + 登录 cookie）。**带有效 cookie 时 blivedm 自动以登录身份初始化，B站返回完整弹幕用户信息；匿名连接会被打码**——这是全名显示的开关。

## 2. EventRouter：回调只入队

`handler.py` 继承 `blivedm.BaseHandler`，覆盖这些回调：

| 回调 | 处理 |
|---|---|
| `_on_danmaku` | 打包进队列；uid=0 时用 uid_crc32 造伪 uid |
| `_on_gift` | 金瓜子÷1000 折算元；记录礼物缩略图 URL |
| `_on_super_chat` | price 本身就是元 |
| `_on_user_toast_v2` | 舰长（`price` 为**实付总价**金瓜子÷1000）；赠送(source=2)不计收入 |
| `_on_interact_word_v2` | 只记关注/分享/特别关注/互粉（进入、点赞量太大不记） |
| `_on_heartbeat` / `_on_popularity_change` | 人气值推给 RoomClient 内存（采样落库） |

人气值和观众数**不进队列**——它们只需要"最新值"，由 handler 的 sink 回调直接更新 RoomClient 内存变量，采样协程每分钟写一条快照，避免高频更新打满队列。

## 3. 三个协议补丁（handler.py 顶部）

blivedm 没跟上 B站的三处协议变化，我们向它的命令分发表注册回调来接管：

```python
blivedm.BaseHandler._CMD_CALLBACK_DICT["POPULARITY_CHANGE"] = callback  # 人气值新载体
blivedm.BaseHandler._CMD_CALLBACK_DICT["ONLINE_RANK_COUNT"] = callback  # 房间观众（真实同接）
blivedm.BaseHandler._CMD_CALLBACK_DICT["ONLINE_RANK_V2/V3"] = callback  # 高能榜
```

- `ONLINE_RANK_COUNT.data.count` 就是直播间页面右上角的"房间观众"——**项目里所有"同接"都来自它**。
- 高能榜 V3 是 **protobuf**（`data.pb` base64），无官方 schema；`_extract_rank_users` 用通用 wire-format 解析（单层条目 + 昵称启发式）提取 (uid, 完整昵称) 对，喂给 uname_map。

## 4. 打码还原链路（writer.py）

B站隐私用户的消息只有打码昵称 + uid_crc32（= `zlib.crc32(str(uid))`，已实测）。还原分两层：

1. **登录身份连接**（主路径）：cookie 有效时消息直接是全名，无需还原
2. **crc 反查**（兜底）：高能榜/礼物学到的 `uid→全名` 存 `uname_map` 总表；Writer 收到伪 uid 弹幕时算 `crc32(uid)` 反查，命中即改写为真实身份
3. **每日回填**（`maintenance._unmask_history`）：映射表扩充后，把历史打码行批量改写

## 5. Writer：批量事务写库

`_flush` 每秒（或队列来事件时）把积压事件归拢，**一个事务**写完：三类明细 INSERT + user_stats UPSERT + 场次冗余计数 UPDATE。要点：

- `user_stats` 的 UPSERT 同时跟随更新昵称/粉丝牌/舰队等级（`CASE WHEN excluded...`），舰队等级取 `MAX`（历史最高）
- uid=0 且无法识别的礼物/弹幕**不进个人画像**（否则所有打码用户并成一个"假用户"）
- 事务失败整体回滚，不会写半批

## 6. cookie 保活（manager._cookie_keepalive）

每 6 小时（启动时也跑一次）：

1. GET `https://www.bilibili.com/` —— 触发 B站 Set-Cookie 刷新短时效凭据（bili_ticket 约 2 天有效期），aiohttp cookie jar 自动接收
2. GET nav 接口检查 `isLogin` —— 失效则日志告警"请更换 cookie"（采集不断，退回匿名打码态）
3. 刷新出的 cookie 持久化到 `data/cookies.json`，重启时与 config 的静态 cookie 合并（文件值优先）

**运维判据：`journalctl -u bili-monitor-capture | grep cookie` 看到登录态正常即健康；看到警告就该换 cookie 了**（换法见 05 章第 7 节）。

## 7. 每日维护（maintenance.py）

凌晨 04:00（启动时先跑一轮）依次执行：

1. **短间隔场次合并**（v0.2.1）：下播→再开播间隔 ≤ `session_merge_gap_sec`（默认 600s）的历史场次对合并为一场（明细迁移、计数相加、峰值取大），幂等；v0.5 起同步迁移场次的标题记录
2. **历史打码回填**：用 uname_map 改写旧打码弹幕的真实身份
3. **用户画像重算**：窗口（30 天）内按现行口径分层（v0.5 定稿：核心=舰队或场均送礼 ≥10 元，活跃=单场弹幕 ≥10 条，见 06 章第 4 节）；顺带回填昵称
4. **过期清理**：弹幕/互动明细超过保留期删除（`config.toml [retention]`）
5. **WAL checkpoint**：合并日志文件控制磁盘

## 8. v0.2 新增：盲盒计价、表情提取、运行时缓存

### 8.1 盲盒收益口径（handler._on_gift）

B站 SEND_GIFT 的盲盒消息字段语义（易踩坑，blivedm 注释已核对）：

| 字段 | 含义 |
|---|---|
| `gift_name` / `price` | **开出的礼物**名与单价（瓜子） |
| `blind_gift.original_gift_name` / `original_gift_price` | 盲盒名与盒价 |
| `total_coin` | 实付总价 = 盒价 × 数量（普通礼物 = 单价 × 数量） |

主播收益按开出的礼物计：`price × num / 1000`。`price` 缺失时的兜底链见
`handler.py` 的 `_on_gift` docstring——最终落到 `blind_gift_prices` 映射表
（由 `/api/blind-box` 接口维护；原管理页面已于 v0.5 移除，实测消息自带 price
覆盖率接近 100%，兜底极少用到）。落库时 `name` 存开出礼物名、`gifts.blind_box` 存盲盒名。

### 8.2 表情提取（handler._extract_emots + emotes 表）

弹幕的 `text` 保留原文（含 `[大笑]` 占位符），表情图片 URL 存 `danmaku.emots`
（JSON `{占位符: {url,width,height}}`），来源三路：

1. 混合弹幕内嵌表情包：`info[0][15].extra.emots`（key 即文本占位符）
2. 纯表情弹幕：`dm_type == 1` 时 `emoticon_options` 直接带 URL
3. 基础表情（`[大笑]` 等）：消息不带 URL，查 `emotes` 表——B站
   `GetEmoticons` API 按房间返回全部表情（基础+房间专属包，各 500+ 个），
   manager 的「表情表拉取」循环定期写表（`config: capture.emoticon_refresh_hours`，默认 24h）

### 8.3 RuntimeCaches（caches.py）

`blind_gift_prices` 与 `emotes` 两张低频变更表的全量内存镜像：
handler 回调运行在事件循环线程、每条弹幕都可能查表情表，dict 直查比
逐条 SELECT 稳。刷新时机：名单热加载循环每 30s 一次（感知管理页改价）+
表情拉取写表后一次。

### 8.4 分层实时更新（writer._SQL_USER_UPSERT）

v0.1 的分层只有每日维护重算，当天新用户全显示"普通"。v0.2 起 UPSERT
语句实时跟进分层（付费即核心、发弹幕升活跃）。**v0.5 起口径调整**：
舰队消息立即升核心、当条场次送礼累计 ≥10 元升核心、当条场次弹幕计满 10 条
升活跃——实时侧是权威口径的必要超集，次日凌晨重算收敛（规则见 06 章第 4 节）。

### 8.5 短间隔场次合并（v0.2.1）

主播短时间内下播又复播（网络波动/换设备被状态轮询误判）会产生碎片场次。
两层防御：

1. **运行时不拆场**（`manager._open_or_adopt_session`）：检测到开播时，
   若上一场结束不足 `capture.session_merge_gap_sec`（默认 600s），直接重开
   该场次（end_time 置空）继续记录，根本不产生第二条；
2. **回溯合并**（`maintenance.merge_short_gap_sessions`）：历史数据里符合
   间隔条件的场次对，把后一场的明细（danmaku/gifts/interactions/
   popularity_snapshots）全部改指前一场，冗余计数相加、峰值取最大、
   end_time 取后一场，再删除后一场。随每日维护反复执行（幂等）。
