# 01 构建思路

## 需求

用户(2026-10-13):在服务器上检查监控直播间的开播状态,开播/下播时向对应 QQ 群发消息提示。

## 技术选型(为什么是 NapCat)

| 候选 | 结论 |
|------|------|
| QQ 官方机器人(开放平台) | 排除:群主动消息额度极少(每群每月个位数条),撑不起"开播突发推送" |
| **NapCatQQ(OneBot 11)** | **采用**:基于真实 NTQQ 客户端的协议端,维护活跃,OneBot 11 标准 HTTP API(`send_group_msg` 一发即中);Linux 无头原生(官方口径内存 50~100MB) |
| Lagrange.Core | 排除(2026-10 调研):官方签名服务停摆,生态萎缩 |
| go-cqhttp / OpenShamrock | 前者停维护,后者需安卓环境 |

风险共识:第三方协议存在腾讯风控,专用小号承担;缓解手段见 03 章保活体系。

## 架构(单向数据流)

```
[B站 get_info] ←15s轮询─ live-qq-notify ─翻转→ [NapCat OneBot :3000] → QQ 群
                      ↑每轮读热配置
              共享 live.db(rooms 只读 / qq_notify 两表读写)
                      ↑写
          bili-monitor 页面(开关/齿轮弹窗/扫码登录)
```

关键决策(经真实事故或用户定稿,决策细节见各章):

1. **房间名单 = bili-monitor 监控列表**(rooms 表,单一事实来源),不自有维护;
2. **全部业务配置入共享库**(`qq_notify` 房间级/`qq_notify_global` 全局单行),
   页面改完最迟一轮(15s)热生效;进程级参数(库路径/轮询节奏)才进 config.toml;
3. **状态机固定规则**:首见静默(宁漏发不重发)、下播防抖 300s(窗口内下播视为闪断,
   **状态不翻转**——防"闪断+复播"连发两次开播)、轮播(live_status=2)归未播;
4. **开播起点用接口 `live_time`(真实本场开播时间)**,防抖窗口与 {duration} 时长都按
   真实开播计(修复"中途开通知的房间以首见时刻当起点"导致的短场漏发);
5. **模板变量体系**:`{uname}{title}{url}{cover}{duration}` 全部纯模板变量,写在文案里
   才有;封面 = CQ 图片码(NapCat 下载发送),主播名取 rooms.anchor_name(get_info 的
   uname 在播时为空);
6. **发送可靠性**:每轮探活熔断(NapCat 掉线则整轮不发);**翻转瞬间掉线就地等待重连
   ~60s**(覆盖密码自动重登时长);超时放弃**不补发**(用户定稿口径);
7. **B 站接口必须小写 `get_info`**——驼峰 `getInfo` 已被网关下线且返回 HTTP 200 +
   `code:1000003 data:{}`,曾整晚被静默解析成"未播"全漏发(2026-10-14 事故);
   现 `code!=0` 一律按查询失败记 WARN,绝不静默当未播。
