# 05 部署到服务器

完整记录一次从零部署（已在 2026-09-12 实际执行通过），以及日常运维方法。

> **⚠ v2.2 架构改版（2026-10-12）**：capture 采集进程与录制/转码/上云管线已
> 整体迁 replay 项目（本文对应章节为历史口径，操作以 replay/deploy/README.md
> 为准）；本项目仅剩 web 服务，共享数据库经 [server].db_path 指向
> /opt/replay/data/live.db。高能时刻功能已移除。

以下占位符（`<服务器IP>` / `<SSH私钥路径>` 等）按你自己的服务器信息替换：

```bash
ssh -i "<SSH私钥路径>" root@<服务器IP>
```

## 1. 同步代码

本机 Git Bash 无 rsync，用 tar 管道（增量、排除本地产物）：

```bash
cd <本地项目目录>
tar czf - --exclude .venv --exclude __pycache__ --exclude data \
         --exclude config.toml --exclude web-example --exclude "*.log" \
         --exclude tests . \
  | ssh -i <密钥> root@<服务器IP> "mkdir -p /opt/bili-monitor && tar xzf - -C /opt/bili-monitor"
```

排除项说明（v0.2 起固定口径）：`data/` 是本地开发库和保活 cookie（服务器独立产生）；`config.toml` 含登录 cookie 与口令，**始终不同步**——首次部署时在服务器上从 `config.example.toml` 复制并按第 3 节填写，之后两端各自维护；`web-example/` 是布局参考图；`tests/` 是本地测试脚本。

## 2. 重建 Python 环境

```bash
# 服务器安装 uv（首次）
curl -LsSf https://astral.sh/uv/install.sh | sh && cp ~/.local/bin/uv /usr/local/bin/

cd /opt/bili-monitor && uv sync
```

**关键点：blivedm 依赖是本地 wheel**（`vendor/blivedm-1.1.7-py3-none-any.whl`，pyproject 指向它）。服务器连不上 GitHub，git 依赖会失败——所以第一次部署时在本地把 blivedm 打成了 wheel 随项目分发。升级 blivedm：本地 `uv add "blivedm @ git+..."` → 从 uv 缓存重新打包 wheel → 改回本地 wheel 依赖 → 同步。

## 3. 服务器侧配置

首次部署时在服务器上创建配置并填写与本地不同的三处：

```bash
cd /opt/bili-monitor
cp config.example.toml config.toml
sed -i 's|^root_path = ""|root_path = "/bili-monitor"|' config.toml   # ① Nginx 前缀
vi config.toml   # ② 填 cookie（浏览器 F12 复制整行）；③ admin_password 填随机口令
```

`admin_password` 非空即启用强制登录（v0.5 起）：未登录页面 302 跳 `/login`、API 401；
同时它是 `X-Admin-Token` 兼容通道的口令（明文记录在本地 `deploy/credentials.txt`，不入 git）。
Web 登录的管理员账号/游客码由服务首次启动自动播种，明文一次性写
`data/web_credentials.txt`（首次启动自动生成）。

## 4. systemd 服务

```bash
cp /opt/bili-monitor/deploy/bili-monitor-capture.service /etc/systemd/system/
cp /opt/bili-monitor/deploy/bili-monitor-web.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now bili-monitor-capture bili-monitor-web
```

两个单元都设了 `Environment=PYTHONUNBUFFERED=1`（否则 print 日志被缓冲，journalctl 看不到）和 `MemoryMax`（capture 400M / web 200M，小内存机器保护）。

## 5. Nginx（注意：并入 default_server）

**坑**：IP 直接访问时 Host 不固定，独立 server 块不会被选中，location 必须放进 `/etc/nginx/conf.d/00-default.conf` 的 `default_server` 里；且 `proxy_pass` **不带末尾斜杠**（保留 `/bili-monitor` 前缀转发），与应用的 `FastAPI(root_path="/bili-monitor")` 配套——若剥掉前缀，页面路由正常但 `/static` 静态资源会 404（实测踩坑）。完整内容见 `deploy/nginx-bili-monitor.conf` 存档：

```nginx
# 00-default.conf 结构：
server {
    listen 80 default_server;
    server_name _;
    location / { return 404; }          # 兜底 404（不能写成裸 return，会拦截所有 location）
    location /bili-monitor/ {
        proxy_pass http://127.0.0.1:8001;    # 不带斜杠：保留前缀，配合 app root_path
        ...（WebSocket 头等见存档文件）
    }
}
```

访问控制（v0.5 起）由应用内登录页承担（签名 Cookie + 登录中间件），Nginx 层的 Basic Auth 已移除——htpasswd 文件保留在服务器 `/etc/nginx/.htpasswd_bili`，需要回退时在 location 里加回 `auth_basic` 两行即可。

改完：`nginx -t && systemctl reload nginx`。

## 6. 部署验收（四项全过才算完成）

```bash
systemctl status bili-monitor-capture bili-monitor-web   # ① 双服务 active
ss -tlnp | grep 8001                                     # ② 仅 127.0.0.1:8001
nginx -t && systemctl status nginx                       # ③ 配置有效
curl -I http://<服务器IP>/bili-monitor/               # ④ 未登录 302 跳 /login；浏览器登录后各页 200
```

（v0.5 前此处为 Basic Auth 401/200 验收，登录体系上线后改为上述口径；完整验收还包括管理员/游客登录矩阵与游客写操作 403，见 06 章第 7 节。）

房间名单在服务器新库里是空的，两种方式添加：页面"直播间管理"（管理员登录后操作），或直接写库：

```bash
cd /opt/bili-monitor && .venv/bin/python -c "
from bili_monitor.db import init_db, connect, now_iso
init_db(); conn = connect()
conn.execute(\"INSERT OR REPLACE INTO rooms (room_id, anchor_name, enabled, created_at) VALUES (?, ?, 1, ?)\", (房间号, '', now_iso()))
conn.commit()"
# 主播名/头像 2 分钟内自动补全
```

## 7. 日常运维

**看状态**：

```bash
systemctl status bili-monitor-capture bili-monitor-web       # 服务存活
journalctl -u bili-monitor-capture -f                        # 实时日志（开播/下播/保活）
journalctl -u bili-monitor-capture | grep cookie             # cookie 健康度（每 6h 一条）
```

**登录凭据**（v0.5 起）：明文在 `/opt/bili-monitor/data/web_credentials.txt`（首次启动自动生成）。忘记管理员口令：登录服务器删 `data/live.db` 中 `admin_users` 对应行后重启 web 服务（会重新播种并写凭据文件）；重置游客码：管理员登录后调 `POST /api/admins/reset-guest-code`。

**换 cookie**（出现"cookie 已失效"告警、或页面弹幕全打码时）：

1. 浏览器登录 B站 → F12 → Network → 任一请求 → Request Headers → 复制 `cookie:` 整行
2. 本地与服务器 `config.toml` 的 `cookie = "..."` 替换；**并删除服务器 `data/cookies.json`**（旧刷新值会覆盖新 cookie）
3. `systemctl restart bili-monitor-capture`，日志确认"登录态正常"

**更新版本**（本地改完代码并自测后）：

```bash
# 1. 同步（同第 1 步）
# 2. 服务器：uv sync（依赖有变时）
# 3. 重启：systemctl restart bili-monitor-capture bili-monitor-web
# 4. 重跑第 6 节验收
```

**数据库维护**：

- 库文件 `/opt/bili-monitor/data/live.db`；每日维护自动清理过期明细 + WAL checkpoint
- 备份：`scp root@<服务器IP>:/opt/bili-monitor/data/live.db .`（建议低峰期，或用 `sqlite3 live.db ".backup 'backup.db'"` 在线备份）
- 磁盘参考：90 天明细约 1-3GB/10 房间，40G 盘充裕

**回滚**：代码无版本化部署目录，回滚 = 重新同步旧版本代码 + 重启（数据库向前兼容，所有表结构变更都有幂等迁移）。

## 8. 重启托底与数据回灌（v0.6.2）

按工作区 AGENTS.md「服务器重启的数据保全规程」（五步细则见本项目 `AGENTS.md`，
本节含完整命令与工具要点）：计划内重启服务器且有直播进行时，
用 `deploy/backfill_local_data.py` 让本地测试端顶住重启窗口，事后把数据并回服务器。
完整流程（本地 Git Bash 执行）：

```bash
# ① 版本对齐：确认本地代码不落后（见工作区 AGENTS.md「跨机同步」章节）
git fetch origin && git status        # 落后则 git pull --ff-only

# ② 取快照 + 记边界（SQLite 在线备份，不中断服务器采集；旧本地库自动滚动备份）
uv run python deploy/backfill_local_data.py snapshot

# ③ 核对本地 config 的房间清单 / cookie 与服务器一致后，启动本地托底采集
uv run python -m bili_monitor.capture.main

# ④ 重启服务器（经用户确认）：ssh root@<服务器IP> "reboot"；服务恢复并
#    验收后，立刻 Ctrl+C 停掉本地采集（越早停，重叠窗口越小）

# ⑤ 打包本地窗口期新数据，合并回服务器库
uv run python deploy/backfill_local_data.py export
uv run python deploy/backfill_local_data.py apply --dry-run   # 先预览
uv run python deploy/backfill_local_data.py apply             # 正式回灌
```

工具要点（完整设计见脚本头部注释，行为由 `tests/test_backfill.py` 的 26 项断言覆盖）：

- **snapshot**：拉取服务器一致快照到本地 `data/live.db`，并把"各表 max id + 时间
  下限"写入 `data/backfill-stamp.json`——这是后续去重与场次归属的边界依据；
- **重叠去重**：服务器采集开机自启，早于我们能停本地端，必然存在重叠窗口
  （同一事件两侧各记一条）。工具按精确键分组后做时间容差配对（默认 ±5s，
  容忍两机时钟偏差），配对上的不导入；"同键连发多条"（如刷屏弹幕）不会被误吞；
- **场次不拆**：快照前的场次沿用同一 session_id；窗口内本地新建的场次按
  "同房间 + 开播时间接近（≤600s，与采集端 session_merge_gap_sec 同口径）"映射
  到服务器新场次，映射不上（如整场直播都发生在窗口内）则插入为新场次；
- **计数与峰值**：冗余计数按实际导入条数增量、峰值取最大（与每日维护的合并
  逻辑同口径，不按明细重算）；end_time 仅当本地记录更晚时延长；
- **幂等与并发安全**：同一回灌包重复 apply 零导入；合并全程单事务
  （busy_timeout 30s），可与在线的服务器采集并发执行；apply 成功后 stamp
  自动消费（改名 `.done-*`），失败则保留可重试；
- **user_stats 不回灌**：每日维护全量重算会自然并入新导入的明细。
